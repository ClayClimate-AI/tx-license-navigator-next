The main flow, idea to shipped

Work top to bottom. Stages with a grey edge are optional.

  1. 0

    Set up the repo, once

    you type
    /mattpocock-skills:setup-matt-pocock-skills
    When
    First time using the engineering skills in a repo.
    Leaves
    docs/agents/ (where tickets live) and an "Agent skills" section in CLAUDE.md.
    Time
    5–10 min. Pick "local markdown" for solo projects.
  2. 1

    Learn the new concepts

    you type
    /mattpocock-skills:teach/mattpocock-skills:research
    When
    The build uses 1–3 things you've never used. Set the assignment as the mission.
    Where
    teach in its own folder (e.g. ~/learning/prisma). research in the repo.
    Time
    About 1 hour, time-boxed. Start the weekend before.
  3. 2

    Decide

    you type
    /mattpocock-skills:grill-with-docs
    When
    Before any code. It interviews you until every decision is made.
    Leaves
    CONTEXT.md (glossary of your project's words) and decision records.
    Done when
    No open questions, and you confirmed the summary.
    Time
    1–3 hours for a week-sized build. Less for one feature.
  4. 3

    Test a design question

    /mattpocock-skills:prototype
    When
    A question needs something you can click to answer: a state model, or what a screen should look like.
    Leaves
    Throwaway code on its own branch, plus the answer written down.
    Time
    30–90 min.
  5. 4

    Write the spec

    you type
    /mattpocock-skills:to-spec
    When
    Right after grilling, in the same session. No new interview.
    Skip if
    You already have spec files (like this week's docs/spec/).
    Time
    10–15 min.
  6. 5

    Break into tickets

    you type
    /mattpocock-skills:to-tickets
    When
    The build takes more than one session.
    Leaves
    One file per ticket. Each ticket is one thing a user can do, through every layer, and lists what blocks it.
    Done when
    You approved the size and order of the tickets.
    Time
    15–30 min.
  7. 6

    Build one ticket at a time

    /mattpocock-skills:implement
    How
    Pick a ticket whose blockers are done. Work it in small steps: ask, review the diff, accept, test, commit. /clear between tickets.
    Careful
    implement writes tests first and commits by itself. To stay in control, say "work ticket 03 in small steps, don't commit" instead.
    Along the way
    wizard for steps only you can do, diagnosing-bugs when stuck, wait-what when lost.
    Time
    Most of the build. Usually 1–3 hours per ticket.
  8. 7

    Check it's done

    /mattpocock-skills:code-review
    When
    When a feature is finished, and once before you ship. Not on every step; your diff review covers that.
    Checks
    Does the code follow your repo's rules? Does it match the spec?
    Time
    About 30–45 min including fixes.

Time budget for the process

What the skills cost on top of writing code, for a week-sized build. Plan for it before you start.

StageTime
Set up the repo (once)5–10 min
Learn the new concepts~1 h
Grill1–3 h
Spec and tickets25–45 min
Code review before shipping30–45 min
Process totalAbout 3–5.5 h

Add the process total to your build estimate, then count back from the due date. A 15–18 hour build plus 4 hours of process is a 3-day job, so start on Saturday for a Friday demo, not Wednesday.

Size the process to the work

Small fix

Just ask. Review the diff.

One-session feature

Grill, then build in the same session.

Multi-session build

The full flow: grill, spec, tickets, build each ticket, review.

Huge and unclear

/mattpocock-skills:wayfinder plans it first, then join the flow at the spec. Rare.

Between stages

At the end of a stage, choose one before you start the next:

ChoiceWhen
Keep goingThe next stage needs what's in this conversation. Stay in one session from grilling through tickets.
/clearBetween tickets. The ticket file and CLAUDE.md carry everything needed.
/compactThe session is getting long but you still need its thinking.
/mattpocock-skills:handoffMoving to a different folder, tool, or person.

Rules that save you trouble

  • Skills marked "you type" never start on their own. If you want one, type it.
  • Run teach outside your app's repo. It creates lesson folders wherever it runs.
  • implement commits by itself. Say "don't commit" if you run git yourself.
  • Spec files only help while they're true. When a step changes a decision, update the spec in the same step.
  • If you can't hold the whole change in your head, write it down before the agent builds it.
